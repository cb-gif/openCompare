## 开发环境

当前仓库是 Rust workspace，尚未创建 Tauri 前端。已有工具要求见 Cargo.toml 与 rust-toolchain.toml；工具链实际可用性以本机检查为准，不能把历史 .tools 安装记录当成现状。

- Rust：当前 MSRV 为 1.88，工具链文件目前使用 stable；FND-00 将确定并固定实际开发版本。
- Windows：Git Bash、Rust MSVC 工具链和对应 C++ Build Tools；未来桌面需要 WebView2。
- macOS：Rust 和 Xcode Command Line Tools；正式签名发布另需发布凭据。
- Node.js：用于现有辅助脚本；前端在 FND-00 选择相容的受支持 LTS 与 pnpm 版本并固定。
- 前端依赖、package.json、pnpm-lock.yaml 和前端命令尚不存在，不运行臆造的 pnpm 脚本。

Windows 的 agent 执行必须按所在环境 AGENTS 的 Git Bash 启动方式工作，不切换到 WSL。下方命令假定已处于项目根目录的 Git Bash；macOS 使用本机 shell。

已有 Rust 检查：

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo build -p compare-gui -p compare-cli
```

文档检查：

```bash
node docs/dev/scripts/check-docs.mjs --self-test
node docs/dev/scripts/check-docs.mjs
git diff --check
```

FND-00 建立前端后，应在真实 package.json 中提供 dev、build、typecheck、lint、test、contracts:generate 等脚本，并在本节补充可运行命令。FND-07 将相关检查纳入双平台 CI。在此之前，不把目标检查记成当前 CI 已执行。

## 任务领取与变更范围

1. 从 plan.md 选择最小可验收节点，核对依赖和源码现状；普通小修复可以先做，再关联现有节点，避免为了格式拆出无意义任务。
2. 开始实质修改前记录目标、涉及目录/文件、接口变化和验证方法。进行中状态可写在节点备注；任务 ID 保持稳定。
3. 多人并行时按节点与文件范围分工，提前约定 DTO、锁文件、主题、共享配置的负责人。不要让两个 agent 同时重写同一文件；需要交接时说明未提交改动。
4. 先约定输入、输出、状态归属与错误行为，再完成一条可运行流程。实现必须同时检查调用方、测试、样本、配置与文档。
5. 完成后提供具体证据；未验证平台、外部资源缺失或部分实现保持未勾选，明确下一步，不把“代码已写”当成交付。

计划状态只在 plan.md 维护；产品文档描述能力与边界，不复制另一份完成清单。跨模块决策更新架构文档，变更需求范围先更新产品规范与节点验收条件。

## 分支与集成

- 先检查工作树、当前分支、上游和用途；只在开发分支修改功能。保留他人未提交内容。
- 不按分支名称猜用途。来源、目标或角色有歧义时先只读核查，只暂停相关分支操作。
- 未获明确授权，不把环境/中间分支通过 merge、rebase、pull、cherry-pick 或补丁引入开发分支。
- 有集成授权时先 fetch，从目标环境最新远端创建或核实复用 `<开发分支完整名称>-<环境标识>`；仅在该中间分支集成。
- 推送前核对远端和 ref，仅显式推送已授权中间分支到同名远端。禁止直接修改/推送环境分支、强推、删除或批量 refspec。
- 普通开发任务不隐含 commit、push、MR/PR、发布或证书配置授权；这些操作按当前会话授权范围执行。

## 实现规范

### Rust 与文件操作

core 保持纯计算，fs 处理原生路径与受保护写入，app 处理状态和流程。宿主命令不重复实现业务。优先沿用现有类型与函数，只在有两个真实调用方或清晰边界时提取抽象。

可预期错误返回结构化 Result，不用 panic/unwrap 处理文件输入、权限或 IPC。长任务必须有预算、可见进度与取消边界；不能在 UI 线程运行扫描或复制。所有写入经过同一保护路径，禁止 UI 绕过预览和磁盘变化检查。

### 前端与视觉

开启 TypeScript strict，禁止用 any 或强制断言掩盖边界错误。Rust DTO 生成文件不手改；开发模式 mocks 不能成为正式命令路径。正文保留在编辑器，React 只存 UI 摘要；遵守架构中的文档/任务版本约束。

复用组件和语义 token，不新增平行主题或第二套弹窗库。按钮包含可访问名称与焦点态，差异不只用颜色表达。用真实内容验证空态、加载、失败、长路径、窄窗口和深浅主题；截图不能代替操作验证。

### 依赖与配置

先用标准库、平台能力或已安装依赖。新增依赖说明实际用途、维护状态、许可证和打包体积影响，检查双平台可用性；不为数行逻辑增加包。正常代码改动不顺便全量升级锁文件。

所有可持久化结构带版本并测试迁移；配置、恢复草稿和日志是不同数据类别。无授权不提交私人样本、密钥、绝对用户路径或文件正文日志。

## 验证、评审与交接

按 [质量规范](quality.md) 运行受影响检查；Rust 改动运行 fmt、Clippy 和相关测试，跨模块变化补 workspace 检查。前端改动运行真实存在的类型检查、测试与构建；涉及系统能力必须注明原生平台证据。文档任务运行文档检查，不因未改 Rust 而假造一次 Rust 测试通过。

评审优先看数据保护、状态竞争、跨平台行为和用户可见结果，再看结构。共享文件或保存/复制变更由另一维护者复核具体差异与证据；AI 自查不替代已约定的人工发布验收。

交接至少包含：任务 ID、完成行为、修改范围、接口变化、实际检查结果、尚未验证项和接续入口。持久化记录遵循质量规范的结果记录规则，不保存日常对话或执行流水。PR 若另获授权创建，描述应让未参与讨论的人理解触发条件、修改行为、验证和限制。

## 使用共享 skill

仓库内的 .agents/skills/opencompare-development 仅保留 skill 注册与加载指令，具体流程统一维护在 [ai.md](ai.md)，随代码版本共享。支持仓库 skills 的 agent 可发现并使用；发现时机取决于工具版本，必要时在项目中开启新会话。根 [AGENTS.md](../../AGENTS.md) 提供统一入口。

调用示例：

```text
使用 $opencompare-development 实现 plan.md 中的 FND-00，先核对依赖与当前状态，完成后记录真实验收结果。
使用 $opencompare-development 修复保存时外部修改被覆盖的问题，更新相关测试和节点证据。
使用 $opencompare-development 审查 TXT-03 的改动，仅报告问题，不修改代码。
```

其他 AI 工具如果不支持 skill 自动发现，直接从根 AGENTS.md 加载 ai.md 和任务相关规范即可。不要求每个工具都维护一份重复规则。skill 不能扩大用户任务范围或替用户批准推送/发布。
