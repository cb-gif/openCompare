# 打包与发布规范

## 发布目标

参考成熟 Tauri 项目的平台/架构分包方式，首版固定三个目标，不把多种格式数量当作兼容能力。

| 目标 | Rust target | 首选产物 | 发布验收 |
| --- | --- | --- | --- |
| Windows x64 | x86_64-pc-windows-msvc | NSIS setup.exe | 实机安装、启动、卸载、升级；WebView2 检查 |
| macOS Apple Silicon | aarch64-apple-darwin | DMG，内含 .app | arm64 实机安装、启动、Gatekeeper、升级 |
| macOS Intel | x86_64-apple-darwin | DMG，内含 .app | x64 实机或明确记录的目标环境验收 |

以上是目标，不是当前已构建或已支持声明。FND-00 先记录暂定最低 Windows/macOS 与 WebView 范围及依据；REL-01 再结合锁定依赖、构建部署目标和三目标实际验证，最终确定并公布最低系统版本与正式支持矩阵。发布说明列出已测版本；暂定下限或 M0 在某台机器启动成功不等于正式支持。

MSI 面向企业分发有明确需求后增加；Windows ARM64、便携包、macOS universal、Linux 后置。cross-compile 成功不等于目标平台验收，Rosetta 结果不能冒充 Intel 实机结果。可用硬件不足时保留对应包为待验收，不静默降低门槛。

## 环境与发布资源确认

本表是发布资源的唯一记录位置，FND-00 负责调查与填写，REL-01 负责复核并补最终验证。当前没有足以确认下列版本、设备、负责人或签名条件的证据，未知项保留待确认。

| 目标 | 暂定最低 OS / WebView 与依据 | 目标测试环境 | 验收负责人 | 签名资源可用性 |
| --- | --- | --- | --- | --- |
| Windows x64 | 待确认：Windows / WebView2 范围 | 待确认：OS、硬件/架构、WebView2 与访问方式 | 待确认 | 待确认：代码签名证书与可用发布环境 |
| macOS arm64 | 待确认：macOS / 系统 WebView 范围 | 待确认：Apple Silicon 实机与系统版本 | 待确认 | 待确认：Developer ID、notarization 与发布环境 |
| macOS x64 | 待确认：macOS / 系统 WebView 范围 | 待确认：Intel 实机或明确记录的目标环境 | 待确认 | 待确认：Developer ID、notarization 与发布环境 |

FND-00 对已确认项记录依据与确认日期；未知项写明缺口、取得验证的途径和待认领负责人，不猜测账号、设备或凭据。其验收要求完成调查记录和所需双平台开发启动，不要求提前完成三目标正式发布；资源缺口仍限制后续对应目标的验收。

缺测试设备、签名凭据或目标验证时，可在实际可用环境生成明确标识架构、签名状态和限制的内部测试包。内部测试包不得标作稳定版、正式支持或据此勾选 REL-01/REL-02。正式首发仍要求上表三个目标达到既定标准；无法满足时保持待验收，不能静默删减目标。

## 产物与安装行为

采用 openCompare 产品名和一致的版本号，文件名目标为：

- openCompare-<version>-windows-x64-setup.exe
- openCompare-<version>-macos-arm64.dmg
- openCompare-<version>-macos-x64.dmg

最终命名由打包配置实现并与 README 保持一致。每次发布附 SHA-256 校验值、变更说明、已知限制、系统/架构矩阵和许可信息。Windows 安装包检查 WebView2；在线下载与离线安装策略需明确，不能在离线机器上只报未知错误。

应用标识在 FND-00 固定，REL-01 验证产物与该标识一致。配置使用平台应用数据目录，安装升级保留配置；卸载是否保留数据必须说明，不能默认删除用户比较的文件。升级验证覆盖旧配置迁移、损坏/未来版本、已打开实例和失败后仍能启动旧版的边界。

发布前核对应用图标、显示名称、文件版本、菜单和 CLI 命名。现有原型命令 bcompare 不作为正式对外名称，避免与已有工具冲突；GIT-01 统一为 opencompare 并同步帮助与测试。

## 签名与分发

- Windows 正式包使用可信代码签名；macOS 正式包完成 Developer ID 签名、notarization 和 stapling 验证。
- 签名凭据与证书存放于发布环境秘密存储，不进入仓库、日志或 AI 任务内容。
- 凭据未就绪时可以生成内部测试包，明确标记签名状态；不能称为已完成正式分发。
- 发布任务只处理已确认版本和产物。开发任务不会自动获得发布、证书配置、推送或创建 Release 的授权。
- 首版使用发布页手工下载更新，不默认开启自动更新。若后续加入自动更新，另设更新签名密钥、端点、回滚和故障策略。

## 流水线与发布检查

构建流程在 FND-07、REL-01 实施；当前仓库只有 Windows Rust CI。REL-01 开始时先复核 FND-00 的暂定版本、测试环境、负责人及签名资源；缺口未解决时仍可内部构建，但不能通过正式发布门槛。

1. 冻结版本和依赖锁，使用已记录工具链构建三种目标；运行受影响自动检查。
2. 检查打包资源只来自本地构建，Monaco worker 与语法资源在离线环境可用。
3. 在目标平台执行 [质量规范](quality.md) 的原生工作流、首次安装和升级；签名校验单独记录。
4. 生成校验值、许可证清单、已知问题与兼容矩阵；确认未夹带测试文件、绝对开发路径或凭据。
5. 发布审批只针对已完成检查的具体版本和文件；有授权后才能上传。
6. 发布后验证下载文件、校验值与安装启动。发现严重问题撤回/标记版本并提供可验证修复，不自动改写旧产物。

版本沿用 SemVer；0.x 允许受控接口变更，配置迁移与数据保护仍必须兼容。每个节点验收与发布验收分别记录，代码合并不等于已发布。
